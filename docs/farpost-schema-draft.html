Written from robinsamways.ca's Chat session, 2026-07-25. Design-only — no code in either repo. Grounded in the real, current Mongo/Beanie models read directly from c:\dev\farpost\farpost-api\app\models\ (not guessed), reorganized around the already-resolved Membership design in docs/core-user-model.md and the billing shapes in docs/core-billing-model.md. This is a Postgres target shape for the from-scratch rebuild — none of the current Mongo documents' field layouts are meant to survive as-is, only the domain concepts they represent.

This is a first pass, not a decision. It needs Farpost's own Chat session's domain knowledge and sign-off before anything gets built, same relay pattern that resolved core-user-model.md's open questions. Sections below are flagged resolved (already decided elsewhere, just applied here), my inference/opinion (a reasonable first guess, not confirmed), or left as an open question.

Legend

Mermaid ER notation: || = exactly one, o{ = zero-or-many, o| = zero-or-one, }| = one-or-many. PK/FK annotations appear next to each attribute inside its table box.

Diagram controls: scroll/pinch to zoom, click-and-drag to pan, use the +/−/reset icons in the diagram's bottom-left corner — reset re-fits every table on screen at once.

Relationship reference — one path at a time

The full diagram above is dense by necessity — this is the same schema broken into small, focused pieces, 2-4 tables each, so a single relationship path is easy to follow without the rest of the schema competing for attention. Each card shows only the primary/foreign keys relevant to that path; see the full diagram above for every field.

User → Membership

erDiagram
    USER {
        text id PK
    }
    MEMBERSHIP {
        uuid id PK
        text user_id FK
        text role
    }
    USER ||--o{ MEMBERSHIP : holds

One User can hold any number of platform-wide capabilities — admin, agent, scout, owner — each its own row.

        uuid membership_id PK,FK
    }

Optional 1:1 extension — role-specific fields (brokerage, service area) attach here, not on Membership itself.

Dispatch eligibility is its own attachable capability — present only for Memberships that are dispatch-eligible, not baked into every professional's root shape.

Worked example — one user, several simultaneous relationships

A single person can be a building's owner, a professional dealing with that same building, and the platform's administrator, all at once, with no conflict in this schema — because "who this person is to Farpost" is deliberately split across two independent axes rather than stored as one flat role on USER.

AxisTableAnswersTied to a specific building?
Platform-wide capability MEMBERSHIP "What can this person generically do across all of Farpost?" No — one row per capability held, independent of any building
Per-building relationship STAKE "What is this specific person's relationship to this one building/property/asset?" Yes — one row per relationship, per subject

Neither axis requires, implies, or excludes the other. A USER can accumulate as many MEMBERSHIP rows and STAKE rows as reality actually requires. Concretely, for one person who owns a building, professionally deals with it, and administers the platform:

HatRow(s)
Owner of Building X STAKE: { user_id, subject_type: "building", subject_id: X, role: "owner", kind: "verified_owner" } — a pure per-building fact, no platform credential involved
Platform administrator MEMBERSHIP: { user_id, role: "admin" } — a pure platform-wide capability, unrelated to any specific building
Professional dealing with Building X (agent, scout, ...) MEMBERSHIP: { user_id, role: "agent" } (the generic credential) — and, only if that work is actually being performed on Building X specifically, a second STAKE: { user_id, subject_type: "building", subject_id: X, role: "agent", kind: "manages_listing" }, or a logged SCOUT_VISIT row if the work is scouting rather than a durable listing relationship

This is the actual reason Membership and Stake are kept as two separate tables rather than one "role" field on User: a single flat field can only hold one value at a time, which would force picking "owner" or "admin" or "agent" — breaking exactly this real, ordinary situation. Splitting the two axes is what lets all three hats exist on the same person simultaneously without any special-casing.

What this schema assumes is already settled

  • Membership replaces Professional.roles + the 10 per-role documents. One row per role held, role is plain text (no enum), per core-user-model.md's resolved fork.
  • Stake ports over conceptually as-is — already a well-designed person↔subject pattern, deliberately kept separate from Membership.
  • RoleType stays an optional Farpost-only curation layer on top of Membership.role, not part of the shared package.
  • FULFILLMENT_FEE generalizes Job.payment (the live F22 shape) per core-billing-model.md — this is a real, concrete payoff of that abstraction, not a new idea introduced here.
  • BILLING_SUBSCRIPTION's flat $12/year framing — a real citation, not an unverified assumption, but flagged for a direct one-line reconfirmation since a fresh read of this doc can't verify it standalone. This isn't invented in this doc: per core-billing-model.md, Robin directly overrode Farpost's own previously-planned per-role multi-tier professional subscription model on 2026-07-24, choosing instead a single uniform $12/year plan attached to every User in every project, Farpost included, no role-scoping. It's meant to coexist with, not replace, Farpost's real transactional per-job fee (FULFILLMENT_FEE) — one is a flat account-level fee, the other is per-transaction, same as e.g. a marketplace charging both a membership fee and a per-sale commission. That said: this specific decision lives in robinsamways.ca's own design doc, and a fresh Farpost session reading only this schema draft has no way to verify it's real rather than a Vocare-specific assumption that leaked in unchallenged — worth Robin confirming directly, one line, that Farpost itself is really getting this flat annual charge on top of its existing per-job model.
  • "Scout" needs zero special-casing — confirmed by Farpost's own session, with real history, not inferred here. Scout was briefly modeled as its own peer identity type (alongside Professional/Owner/Admin) during the 2026-07-12 unify-user-identity-model change, was recognized as wrong within about a day, and was folded back into being just another RoleType value inside Professional.roles — the same kind of entry as "adjuster" or "contractor" — via fold-scout-into-professional-roles, proposed and archived the same day (2026-07-13). No standalone scouts collection has existed since. This is real, historical evidence for the already-resolved role: text / RoleType-taxonomy decision (see core-user-model.md): a role concept got fully reconsidered and re-homed with zero schema migration, precisely because roles already live in a flexible, admin-editable taxonomy rather than hardcoded peer types. Someone scouting a building — you, scouting your own, per the earlier example — holds a completely ordinary Membership row (role: "scout"), no different in kind from role: "admin" or role: "agent". ScoutFieldNote continuing to exist as its own model isn't a leftover of the old identity type — it's a legitimate domain object (a work-product/contribution record, same category as a claim or an inspection), distinct from the identity question that already got resolved. That's exactly why SCOUT_VISIT is modeled here as an activity table referencing a Membership, not as its own identity concept.
  • BuildingOwner folds into Membership (role: "owner") — not into Stake, correcting an earlier guess in this doc. Confirmed by Farpost's own session, using its own concrete example (a contractor, "Jane," who also owns her home and helps administer the platform): BuildingOwner's real job today is a platform-wide fact — "this person has completed owner verification" (verified_at) in the abstract, independent of any specific building — the exact same shape as Professional ("this person is a verified, dispatchable contractor," also independent of any specific building) and Admin. All three are additive, independent membership documents keyed only on user_id, with no schema-level exclusivity between them — precisely the pattern Membership already exists to unify. Stake is untouched by this and keeps doing exactly what it already does: "Jane owns this specific building" is still a Stake row (role: "owner", subject_id = that building), separate from the platform-wide Membership fact that she's a verified owner at all. Buying a second building only ever adds a second Stake row — no change to any Membership.
  • Dispatch stops being structurally privileged — pulled out of both Professional and Job, matching a real, already-shipped Farpost correction. Farpost's own history here is directly on point: it began as a dispatch-claims tool, the dispatch-first framing was identified and corrected repeatedly at the docs level (2026-06-21, 2026-06-22, and again 2026-07-03 — the third recurrence is why CLAUDE.md rule 15 exists as a belt-and-suspenders fix after informal correction failed twice), and — the part that matters for this schema — a real 2026-07-03 "dispatch unification" change already demoted dispatch at the code level: claim dispatch was folded into a generic work-request framework (RequestType = claim | inspection_request | service_request; WorkRequestAttempt is a real, already-generic, polymorphic dispatch-attempt log shared across all three) rather than claims keeping their own special dispatch mechanism. My first pass hadn't caught up to this: it had dispatch_* fields baked directly into PROFESSIONAL_PROFILE's root shape, dispatch-attempt fields embedded directly in JOB (implicitly claim-only, since JOB.claim_id was claim-specific), and no INSPECTION_REQUEST entity at all — three ways the diagram was quietly repeating the exact bias being asked about. First correction (superseded by the next item below, which goes one level deeper): dispatch eligibility moved into its own attachable DISPATCH_CAPABILITY table off Membership, and a dispatch-attempt table plus an INSPECTION_REQUEST sibling to CLAIM were added to match the real, already-generic RequestType/WorkRequestAttempt pattern. SERVICE_REQUEST is the third real RequestType value but has no backing model in the code yet, so it stays named in prose only, not given a fabricated table.
  • Job itself generalizes past claim-dispatch, one level deeper than the item above — the same demotion pattern applied again, this time to the thing being dispatched rather than the dispatch mechanism. Flagged directly, with the concrete gap: dispatch itself had already been generalized (WorkRequestAttempt), but Job underneath it still hardcoded claim_id/contractor_id/adjuster_id — assuming a claim always exists and the two parties are always specifically a contractor and an adjuster. That shape can't fit a realtor requesting a field specialist, or an owner requesting a broker — there's no claim, and the roles aren't fixed. Job is now: a request, from any User (requester_user_id, regardless of what Membership rows they hold), for a specific target_role (a RoleType key — same taxonomy Membership.role already validates against), optionally naming or later resolving an assignee_user_id, optionally about an object via the same generic subject_type/subject_id pattern Stake already uses (a claim, a building, a property, or nothing at all — "find me a mortgage" has no tracked subject). INSPECTION_REQUEST is retired entirely, one change later than it was introduced — it's now just an ordinary Job (target_role: "inspector", subject_type: "building"), which is the exact same "two parallel structures for the same concept" pattern already fixed twice elsewhere in this doc (Professional.roles vs. the 10 role tables; BuildingOwner vs. Stake) — resolved here before it could calcify a third time. WORK_REQUEST_ATTEMPT simplifies too: since Job is now the only top-level "thing being dispatched," its own request_type/request_id polymorphism is no longer needed — it references job_id directly. CLAIM flips from wrapping Job to extending it (CLAIM.job_id is now its primary key, mirroring exactly how PROFESSIONAL_PROFILE.membership_id extends Membership) — it keeps only what's genuinely claim-specific (insurer file number, damage info, the property intake snapshot), everything generic having moved up to Job. JOB_NOTES' fields were renamed from adjuster_notes/contractor_notes to requester_notes/assignee_notes for the same reason — a table meant to serve any role pairing shouldn't hardcode which two roles it expects. This makes Job a third instance of the same recurring shape: Membership (person ↔ platform capability), Stake (person ↔ specific object, standing relationship), and now Job (person ↔ person, one-off transactional request, optionally about an object) — three scopes of the same underlying "who, in what relationship, to what, with what status" question.
  • Job.status's vocabulary, checked directly against the real ClaimStatus/JobStatus enums — two distinct problems found, both fixed differently. CLOSED turned out to be genuinely claim-specific and confirmed (not just assumed) to stay off Job.status entirely — it's the insurer-side administrative wrap-up, a real event layered on top of Job.APPROVED/payment-complete, not a job-lifecycle state. Claim.closed_at stays exactly as designed. But NEW exposed a real gap: JobStatus had no pre-dispatch state at all (starting at DISPATCHED), which is incompatible with Claim.job_id being a true 1:1-from-creation primary key — a claim (or a directly-named-assignee job, e.g. "I want this broker") has to exist in a created-but-not-yet-dispatched state. DECLINED/TIMEOUT exposed a second, different problem: they're already tracked per-attempt via DispatchResponse on WORK_REQUEST_ATTEMPT — carrying them on Job.status too would be the exact Professional.roles-vs-per-role-tables bug recurring one layer down, two places recording the same outcome with nothing keeping them in sync. Neither actually captured ClaimStatus.FAILED's real meaning either — "every candidate exhausted, giving up" is terminal, not the same as one attempt's transient decline/timeout. Fixed: Job.status is now pending | dispatched | accepted | in_progress | documented | approved | paid | exhausted — a genuine initial state added, the redundant per-attempt values dropped in favor of WORK_REQUEST_ATTEMPT owning them, and one real terminal failure state added. The full ClaimStatus vocabulary now maps cleanly: NEW→pending, DISPATCHED/ACCEPTED/ IN_PROGRESS/DOCUMENTED/APPROVED unchanged, CLOSED→Claim.closed_at set, FAILED→ Job.status = "exhausted".
  • All 10 real Professional role models checked directly against PROFESSIONAL_PROFILE's consolidation — 9 fold in cleanly, and the one real outlier (Contractor) got generalized rather than special-cased, per Robin's own override of the first recommendation. Farpost's session confirmed Accountant, Adjuster, Agent, Appraiser, Broker, Inspector, PropertyManager are all 1-3 flat optional strings (licence numbers, affiliations) — trivial to consolidate; HomeStager/SpaceCoordinator are explicitly near-empty placeholders in the real code, no domain fields defined yet. Contractor is the real outlier: nested service-area/compliance sub-schemas, a status enum, three credential expiry dates, and — the part that actually mattered — two fields (service_area.postal_prefixes, damage_types) that are genuinely indexed and queried by the real dispatch-matching system, not just stored. The first recommendation was a dedicated Contractor extension table to protect those indexes. Robin rejected that directly — no table just for one role — so it's generalized instead, the same move made repeatedly throughout this doc: DISPATCH_CAPABILITY gains service_postal_prefixes and max_drive_minutes (a second, list-based way of expressing service area alongside the existing radius-based one — any role can use either), its existing capabilities field already covers what Farpost calls damage_types; a new COMPLIANCE_RECORD table (credential_type, expiry_date, status) attaches to any Membership for insurance/WSIB/certification tracking, not contractor-exclusive even though contractors are its first real user; and Membership.status gains a pending value generically (any role can be pending activation, not just a contractor awaiting compliance verification). Net result: still zero tables dedicated to any one role — the real complexity got absorbed into already-generic structures instead.
  • Claim gets its own independent identity instead of extending Job 1:1 — a real correction to v11, found by checking claim_repository.py directly. The real code's set_status treats claim.job_id as a plain, reassignable field, not an immutable shared-key relationship — Claim-extends-Job was too rigid a reading. More importantly, a genuine business scenario doesn't fit 1:1 at all: a follow-up inspection requested against an already-existing claim is a second, distinct piece of work, not a retry of the first. CLAIM now has its own id (dropping the shared job_id primary key), and any number of Job rows can reference it the exact same polymorphic way Stake already points at Building/Property/Asset (Job.subject_type = "claim", Job.subject_id = claim.id) — one dispatch job and a later inspection job can both point at the same claim, no special-casing. Whether Farpost's real workflow actually needs more than one Job per claim in practice is a genuine business-logic call, not resolved here — but the schema now supports either answer without needing to be redesigned later.
  • PostGIS specifics, deferred back to Farpost as expected — SRID 4326 (WGS84) with a GiST index on every geography column, confirmed as the real intended choice, not left genuinely open.
Resolved — not a schema question, and deliberately not solved with one. Nothing in either the current model or this redesign stops the same person from holding an admin Membership and an owner Membership/Stake at once — an admin could personally own a building whose records they also administer. Robin's own call: no technical restriction for now — at Farpost's current scale there's very likely only one real admin in practice, so recusal logic would be defensive code against a conflict with no second party to create it yet. Instead, admin actions should already be logged with enough context (claim_id/job_id/whatever record, per rule 7) that a real conflict would be visible in an audit trail after the fact, if it ever mattered. A lightweight middle option worth keeping in mind, not committed to building now: a UI banner when an admin views/edits a record they hold an ownership Stake on ("you have an ownership interest here") — visibility without blocking anything. Full programmatic recusal (blocking the action outright) stays the heavy option, worth revisiting only once a real second admin exists whose incentives could actually diverge.

    • Feedback — Farpost already has two real senses (in-app feature-usability feedback with AI-generated insights; free-text adjuster/contractor notes on a Job), and Vocare's conversation-engine adds a third (post-session analysis). None of these touch Claim. That's why JOB_PHOTO generalized into JOB_ATTACHMENT (doc_type free text — photo, deed, staging agreement, invoice, whatever a given job actually needs) rather than staying photo-specific: most jobs carry nothing more than a handful of loose documents, not a full structured extension record. Claim keeps its own dedicated table only because Farpost's real code already has a genuinely large, structured field set for it (insurer file number, damage types, the property snapshot) — if some future job type earns that same depth (a "Mortgage" or "StagingAgreement" extension, say), it gets a table the exact same way, with the exact same standing, not a lesser or provisional one.
  • Claim.property stayed as columns on CLAIM, not a link to BUILDING/PROPERTY. Read this as a deliberate intake-time snapshot (address/contact info as known when the claim was filed, which may drift from the building's current record) rather than something that should always resolve live off BUILDING — flagged as an assumption, not verified against any doc explaining the original reasoning.
  • ENGINE_INSTALLATION / ENGINE_ACTIVITY_LINK are new — the suite-consumption objects from this session's conversation (the "admin page with installable components" idea). ENGINE_ACTIVITY_LINK is the join between a Farpost context (a Membership doing something on a Job/Claim) and an external engine's own record (a Vocare session ID) — Farpost never owns or duplicates Vocare's data, just references it.
