# Standard methodology

Robin's own cross-project build methodology — conventions he wants his own independent
applications (Farpost, Vocare, Sreditor, Smallburg, Mr.Commish, and whatever comes next) to
adopt by his own choice, not a structural categorization. Each of these is its own project
in its own repo — none of them is "a piece" or "a silo" of robinsamways.ca. `siloes/` as a
distinct concept is retired entirely (2026-07-25, Robin's own decision) — `pieces/` remains
a robinsamways.ca-only convention for narrow portfolio case-study modules that *showcase*
one of these projects on the portfolio site, and has no bearing on how any of these
projects' own repos are organized or governed. This file describes what Robin wants
carried across his own projects; it is not part of robinsamways.ca's own conventions, which
already have their own `CLAUDE.md`. A living document: add to it as rules get defined or
refined, don't wait for a clean rewrite.

**Stubbed projects:** Smallburg and Mr.Commish are named here only as entries in the project list — Robin hasn't had bandwidth to get back into either and asked that they just be stubbed out for now, not researched or assumed into. Don't invent details about what either one is or does. If a future task genuinely needs to know something about them to proceed, ask rather than guess.

## Development rules

1. **Common tech stack.** Auditing Vocare, Farpost, Sreditor, and Smallburg's actual dependency files found that Vocare had *already* converged on **Fastify + Drizzle ORM + Postgres + better-auth** before that combination was consciously named as "the stack" (`docs/lightbulbs/rsw-lb-own-stack-discovery-dev-log-entry.md`). Farpost and Smallburg are now being deliberately brought toward it. The Fastify half is separately backed by real comparative research against Express (`docs/lightbulbs/rsw-lb-fastify-vs-express-dev-log-entry.md`).

2. **Mobile-first, laptop-second — with a real answer for laptop-second now.** Vocare's own real design is mobile-first: a condensed center column, footer-based navigation, a simple top header for branding, a shape that barely changes between phone and laptop. That's a defensible starting bet, but it left large-screen visitors with a narrow column stranded in a wide viewport (`docs/lightbulbs/rsw-lb-vocare-farpost-desktop-scaffolding.md`). **Resolved 2026-07-26:** the large-screen answer is robinsamways.ca's own left-drawer-nav / sticky-header-center-column / right-rail scaffolding, not a separate invention per project. See rule 3.

3. **Common scaffold/layout — two shapes, one per breakpoint band, not one shape stretched across both.** Mobile keeps Vocare's already-proven house style: a simple header (brand + UI effects) always surfacing sign-in/sign-up/sign-out, plus footer-based primary navigation. Laptop/desktop adopts robinsamways.ca's own real, shipped framing instead of inventing a new one per project: a tiered, collapsible left nav; a center column with a sticky header; a right rail carrying account/settings icons plus an inline "on this page" anchor nav that scans real headings rather than a hand-maintained registry. A full port of the actual current source for this framing — real code, not a description of it — was handed off to Farpost's own repo on 2026-07-26 (`docs/handoff-2026-07-26-farpost-framing-scaffold.md`, robinsamways.ca repo, meant to be deleted from there once picked up). What's genuinely portable (the layout/interaction mechanism) vs. what each project must supply itself (nav content, theme colors, wiring the session-conditional icon to that project's own auth) is called out explicitly in that handoff — don't copy it verbatim without reading which parts are project-specific.

4. **Common core objects/schemas — User designed and closed out, first real answer to this rule.** The root case: Farpost's identity model doubled up on "role" (a `roles: list[str]` field *and* 10 per-role child tables joined by a bare string), because a good later correction (`User`-as-root-identity) landed without removing the old skeleton it replaced (`docs/lightbulbs/rsw-lb-role-modeled-twice-dev-log-entry.md`). `docs/core-user-model.md` (2026-07-24, checked against real code in `c:\dev\vocare\backend` and `c:\dev\farpost\farpost-api`, then closed out with Robin directly) lands on: a shared library (not a shared database) layering better-auth's own `user` table with a generic `Membership` table for "what is this person to this app" — `role` is plain `text`, no enum, no admin-curation apparatus in the shared package. Farpost's original goal for runtime-editable roles (let a user claim a real-life role — e.g. "home security professional" — the platform hasn't built dedicated support for yet) is satisfied by unconstrained text alone; any curation/moderation on top is Farpost's own optional extension, not shared infrastructure. better-auth's Organization/Admin plugins are ruled out entirely (no multi-tenant shape in any current project). Distributed as a git dependency (`github:robinsamways/core-identity#tag`). The entitlement/tier question is now answered and simplified: `docs/core-billing-model.md` settles on one uniform $12/year entry subscription across every project, attached directly to `userId` with no role-scoping — deliberately overriding Farpost's own documented "base platform free forever" strategy for the rebuild, per Robin's explicit call to keep this simple rather than preserve a philosophy that contradicts the new pricing. Further revenue comes exclusively from Pattern 2's one-time actions — a postpaid fulfillment fee (generalizing Farpost's live per-job platform-fee invoice) and a prepaid credit pack (Vocare's "session packs" and Farpost's own unbuilt "tokens" lightbulb turned out to be the same shape independently). Farpost's originally-planned multi-tier professional subscriptions were dropped in favor of this simpler, repeatable shape. Other core objects (beyond User/billing) remain undesigned.

5. **Offline-first where applicable.** Not yet explored anywhere — genuinely new with this rule, no existing groundwork to point to.

6. **Development practices — carry the process discipline, not just the stack.** robinsamways.ca's own working model, proven across many real changes, is what Robin wants adopted on his other projects too, not just the tech choices in rules 1-5:
   - **Spec-before-code.** A proposal, a design doc for anything with real technical decisions or ambiguity, explicit requirement/scenario specs, and a task checklist — written and agreed before implementation starts, not reconstructed after the fact. OpenSpec is the tool used for this on robinsamways.ca; the discipline (not necessarily the specific tool) is what matters.
   - **A planning role and a building role are different sessions.** robinsamways.ca keeps "architects the change" and "implements the change" as separate, explicitly-assigned session roles rather than one session doing both fluidly — reduces the risk of scope invented mid-implementation without anyone signing off on it first.
   - **Tests ship with the feature, not after.** Representative coverage for whatever behavior a change adds, in the same change, using whatever test framework that layer already has — not deferred to a later retrofit.
   - **A drift audit before anything is considered done.** After implementation, check the real, running result against the spec's actual literal wording — not just "does it work," but "does it work exactly the way the spec says it does." Real, repeated experience on robinsamways.ca: a report that says "verified" or "drift-audited and synced" is not automatically proof this happened completely — spot-check it.
   - **Contemporaneous handoff/issue logging.** A running, dated log of real bugs found, decisions made, and handoffs given — literal enough that a different session (or a different day) can pick up exactly where the last one left off without re-deriving context. robinsamways.ca's `docs/issues.md` is the concrete example of the shape this takes.
   - **A lightweight place to capture ideas that aren't ready to build yet.** One file per idea, not a backlog buried in chat history — so nothing gets lost between when it's noticed and when there's time to scope it.
   - **A trend line on code health, not just a one-time check.** robinsamways.ca tracks lines/complexity/duplication (`scc`) at every real checkpoint specifically to catch creeping duplication early, not just to have a number.
